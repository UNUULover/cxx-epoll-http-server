# 压测报告

所有数字都是在本项目虚拟机里实测得到的，命令附在下面，可以复现。
**先说结论，再说为什么这个结论不能直接用嘴吹成"高性能"。**

---

## 测试环境

| 项 | 值 |
|---|---|
| 宿主 | VMware Workstation 虚拟机 |
| 客户机 | Ubuntu 24.04.4 LTS，kernel 6.8.0-139-generic |
| vCPU | **2**（关键约束） |
| 内存 | 4 GB |
| 编译器 | g++ 13.3.0，`-O2 -g -DNDEBUG`，`-Wall -Wextra` |
| 压测工具 | wrk 4.1.0（epoll 版） |
| 网络路径 | 本机回环（127.0.0.1） |

---

## 一、吞吐：主从 Reactor vs 单 Reactor

`/hello`（固定内存响应，不碰磁盘），`wrk -t2 -c100 -d8s`，每种配置跑 3 次：

| 配置 | run1 | run2 | run3 |
|---|---|---|---|
| `-t 0` 单 Reactor | 11154 | 12732 | 13182 |
| `-t 2` 主从 Reactor | 11757 | 13442 | 13048 |

单位 req/s。并发 1000 时：

| 配置 | run1 | run2 | run3 |
|---|---|---|---|
| `-t 0` | 10346 | 11795 | 11302 |
| `-t 2` | 11477 | 9782 | 12004 |

静态文件路径（`GET /`，`-t 2`，c=100）：10196 / 10400 / 9938。

**结论：两种架构在这个环境下没有可区分的差异。**

## 二、对照实验：同机 nginx

这是理解上面那组数字的关键。同一个 VM、同样的 wrk 参数，跑系统自带的 nginx：

| | run1 | run2 | run3 |
|---|---|---|---|
| nginx | 10656 | 11985 | 12727 |
| ws-server (`-t 2`) | 11757 | 13442 | 13048 |

**nginx 也只有 1 万出头。** 也就是说这个 ~1.2 万的数字是**环境的天花板**，
不是我的服务器实现的上限。

原因很直接：压测端（wrk）和服务端跑在同一台只有 2 个 vCPU 的机器上。
wrk 要跑满一个核才能产生负载，服务端本身又是 CPU 密集的 syscall 路径 ——
两台机器干的活挤在 2 个核里。而 `-t 2` 时服务端有 1 个 accept 线程 + 2 个子 Reactor
线程共 3 条线程，在 2 个 vCPU 上是**超订**的，所以"多线程更快"根本不可能体现出来。

## 三、延迟与并发的关系

`wrk -t1`，不同并发下的表现：

| 并发 | req/s | 平均延迟 | p50 | p99 |
|---|---|---|---|---|
| 1 | 3431 | 287 µs | 210 µs | 1.56 ms |
| 10 | 8321 | 0.94 ms | 704 µs | 3.75 ms |
| 50 | 8033 | 4.06 ms | 3.72 ms | 11.20 ms |
| 100 | 7855 | 7.43 ms | 6.64 ms | 17.53 ms |

两个观察：

1. **并发 1 时单次往返约 240–290 µs**，量级正常（这个数里还包含 wrk 自身的处理开销，
   以及虚拟化环境下偏贵的系统调用）。说明单请求路径上没有病态开销。
2. **从并发 10 往上，吞吐就锁死在 8–13k 不再增长，延迟线性上升** ——
   这是典型的"CPU 打满后排队"曲线，不是服务端某处卡死。

服务端自身的 CPU 占用（`pidstat`，约 13k QPS 时）：

```
平均时间:  %usr 39.43   %sys 44.09   %CPU 83.53
```

不到一个核，但**其中 44% 是系统时间** —— 这台虚拟机上系统调用的代价很高，
这是回环吞吐上不去的直接原因。

## 四、这个结果怎么讲，才算加分而不是露怯

**不要讲**："我的服务器 QPS 到 1.3 万。"（面试官接着问"什么机器、多少并发、跟谁比"，就没了）

**要讲**：

> 我在一台 2 vCPU 的虚拟机上压测，单机 QPS 大约 1.3 万。这个数字说明不了我的实现水平，
> 因为我做了对照实验：同一个环境、同样的 wrk 参数跑 nginx 也只有 1.2 万。瓶颈是压测端和
> 服务端在抢同样两个核 —— `pidstat` 显示服务端自己只占 0.83 个核，且 44% 花在系统时间上。
>
> 我用并发梯度确认了这一点：并发从 10 加到 1000，吞吐锁死在 1 万上下而延迟线性上升，
> 是 CPU 打满后的排队曲线；并发为 1 时单次往返 240 µs，说明单请求路径没有病态开销。
>
> 所以我也没法用这台机器证明"主从 Reactor 比单 Reactor 快" —— `-t 2` 时服务端有 3 条线程，
> 在 2 个 vCPU 上是超订的，两者测出来当然一样。要做这个对比，服务端和压测端必须分开到
> 不同机器上，或者至少给服务端 4 个 vCPU。

这段话把"数字不好看"转成了"我知道我的测量方法哪里不成立" —— 后者才是面试官想看的。

## 五、复现命令

```bash
# 构建
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j"$(nproc)"

# 单 Reactor
./build/ws_server -p 18081 -t 0 -d ./www -i 60 -l /tmp/single.log &
wrk -t2 -c100 -d8s --latency http://127.0.0.1:18081/hello

# 主从 Reactor
./build/ws_server -p 18082 -t 2 -d ./www -i 60 -l /tmp/multi.log &
wrk -t2 -c100 -d8s --latency http://127.0.0.1:18082/hello

# 对照：同机 nginx
sudo systemctl start nginx
wrk -t2 -c100 -d8s --latency http://127.0.0.1/

# 服务端 CPU 占用
pidstat -p "$(pgrep -f 'ws_server -p 18081')" 1 6
```

## 六、还没做的测量

1. **定量的系统调用统计**（计划用 `strace -c -f` 统计每请求的 `read`/`write`/`epoll_ctl` 次数，
   预期是每请求各 1 次 read 和 write、0 次 `epoll_ctl`）。这是"send 里先试写一次"这个优化
   最直接的证据，但本次没有跑出可信结果。
2. **`pending_timers` 的对比**：改掉"每请求重装定时器"之前，这个数应当随请求数线性增长；
   改完之后应当约等于连接数。这是那次改动的验收指标。
3. **≥4 vCPU 下的架构对比**，以及把压测端放到另一台机器上的对比。
4. **长连接下的稳定性**：连续压 10 分钟以上，观察 RSS 是否平稳。
